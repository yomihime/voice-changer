## 対応するソースと構築

公開変更の基準は Server `64c5eeec168a1cc56b18d9b90d49fd9db3475e0f`、Client `661a10a3ce4618ba205f1c0180119e0eca1964c1` です。対応する Client は親 commit の `client/frontend` gitlink に固定します。Client の変更を先にマージし、その commit を取得可能な状態で親変更をマージしてください。

Client 内で次を実行します。Node.js 24.20+（24.x）、Windows 向け Rust/MSVC、WebView2 が必要です。詳細は [TAURI.md](../../client/frontend/TAURI.md) を参照してください。

```powershell
npm ci
npm run build
npm test
npm run test:browser
cargo test --manifest-path src-tauri/Cargo.toml --locked --offline
npm run desktop:build
```

EXE は `client/frontend/src-tauri/target/release/voice-changer-client.exe`、NSIS は同じ release 配下の `bundle/nsis/` に生成します。EXE は毎回 localhost:18888 を確認し、失敗時に接続先を入力できます。入力・出力・監視端は各 PC のデバイス名を確認して選択します。Client Device はクライアント PC、Server Device は backend PC のデバイスです。

## インターフェースと安全性

- `/info` の実フィールドで旧 VCC と 2.x を識別します。旧 VCC の制御を集中変換し、未対応操作は理由付きで無効化します。
- 旧設定は `/update_settings` の FormData を使い、GET 回読と値一致を要求します。複数変更は事前検証後に直列処理します。旧 API に設定トランザクションはありません。
- `/load_model_if_empty` は共有 lock と原子的ディレクトリ予約で既存 slot を保護します。競合時は409、失敗時の部分ファイルは保持します。この能力がない旧 Server では新規登録を無効化します。従来の `/load_model` は既存の上書き仕様を維持します。
- `/test` は JSON / base64 の mono little-endian Int16 PCM です。Float32 変換は Client 境界で一度だけ行い、既存 Server が履歴・resampling・SOLA を担当します。通常 Legacy は同率・同サンプル数、Official の可変出力は別に扱います。
- `/reset_audio` と epoch/sequence で旧フレームと重複を拒否します。有限 warmup、1 inflight + 1 pending、有界入出力キュー、設定変更時の旧ストリーム停止を実装しています。Server Device が所有する音声は Client からリセット・追加送信できません。
- Client Device は Client 終了時に音声を解放し、backend は継続します。Server Device は制御ウィンドウ終了後も継続し、明示停止またはデバイス・backend 故障で停止します。

- 最終音声候補のほぼ無音負荷は1,800.86秒、48 kHz / 6,144 sample、14,084ブロック送受信でした。入出力破棄・音声エラー・backend 推論失敗はいずれもゼロ。出力キュー最大12,288 / 48,000 sample、HTTP 同時処理最大1件です。音声開始前の接続探索時に `/info` の proxy 接続失敗を1件記録しました。稼働中の失敗とは区別します。
- Client プロセスツリーの working set は553→903 MiB、約5分以降は主に860〜905 MiBで変動しました。これは長期メモリ上限の証明ではありません。採取した HTTP RTT は音響端から端の遅延ではありません。

## Legacy の chunkSec 修正

旧 backend の48単位（0.128秒）が選択肢にないため誤表示され、0.1秒の指定が37.5単位として拒否されていました。さらに Device モード切替が古い値を再送する問題がありました。

48 kHz 基準の128フレーム単位に丸め、backend の実値を選択肢に含めます。0.1秒プリセットは38単位 / 4,864フレーム / 約0.101333秒、0.2秒は75単位 / 9,600フレームです。範囲は8〜1,875単位です。一般設定更新から古い raw 値を除き、専用の chunkSec 更新だけがこの値を書き込みます。

実 EXE と隔離 backend で両モードの選択・切替・画面更新・backend 再起動後の保持を確認しました。動作中 Client の変更は旧ストリームを停止し、明示再開後に新しい長さを使います。動作中 Server は先に停止する必要があり、この拒否は回帰試験で確認しています。自動生成した12秒 / 48 kHz / mono Int16 の倍音 WAV を実ファイル選択画面から開き、4,864と9,600フレームで非ゼロ出力を確認しました。

## 既知の問題と未検証

- 旧候補の連続試験で単発 `/test` 502 による停止がありました。現在は native proxy 自身が識別した転送失敗に限り、稼働中 Legacy の連続していない1回を破棄し、次の sequence へ進みます。同じ sequence を再送せず、2回連続失敗で停止します。分岐は回帰試験で確認しましたが、底層502の根因は未確定です。
- マイク入力はほぼ無音でした。真人の有声音と聴感、有声音の長時間負荷、物理的抜き差し、異なるモデル/GPU、音響端から端の遅延、長期メモリ上限、別 PC の LAN は未検証です。
- Windows 音声は共有ダイアログが返す音声トラックを使います。対象ソースを指定したキャプチャは未実施です。トラックがない場合は停止します。
- checkpoint 内部の ValueError が `invalid_resource` に分類される場合があります。登録は明示的に失敗し、ファイルを保持します。

この記録は公開可能な検証要約です。音声・モデル・個人設定・生の診断はソースや構築入力に含めません。

## 間欠的な502の調査

- 旧約710秒試験には、開始前の `/info` 502が1件、稼働中の `/info` 502が3件と停止時の `/test` 502が1件ありました。当時は status/path だけを保存しており、応答本文、OS コード、要求 ID はありません。同じ backend が推論失敗ゼロで応答を続けたことは確認できますが、問題の要求が処理済みかは判定できません。
- 最終1,800秒試験の唯一の `/info` 502は、音声開始前、初期状態の記録より約3秒前の `backend_transport/connect` でした。通常起動時の localhost:18888 探索失敗という説明と整合します。過去の宛先代次が未記録のため断定はできません。今回の実 EXE で、既定ポートにサービスがない場合の探索が同じ `connect` / Windows 10061 を返すことを確認しました。
- 実 EXE の独立 profile と生成 HTTP サーバーで、GET 1,000回、約16 KB の POST 1,000回、5 ms 間隔の POST 1,000回がすべて200、合計3,000要求は同じ TCP 接続を再利用しました。実 VCC の読み取り専用 `/info` 1,000回もすべて200でした。自然発生の502は再現していません。
- 制御実験では、要求受信後の RST が `send/request/ConnectionReset/10054`、拒否接続が `send/connect/ConnectionRefused/10061`、テスト限定の応答待ち timeout が `send/timeout` でした。上流の HTTP 502はそのまま転送し、本文の途中切断は200ヘッダー後の `response_body/decode/UnexpectedEof` として区別しました。RST 後の生成 POST 再送はありません。期限切れ idle 接続を20回実際に作り直す実験も全200でした。
- 最初の小標本で「常に1接続」という試験側の仮定が、成功した25 POSTの6接続で失敗しました。接続分布の計測に修正し、上記の最終実験で再確認しました。この短い観測から長期上界や全 Windows 環境の安定性は推定しません。
- HTTP 転送の失敗時にだけ、安全な要求 ID・接続先代次・段階・分類・経過時間・固定経路名・取得できた I/O / OS コードを追加します。元の例外文字列、URL/query、認証、音声・本文は記録しません。応答にも同じ診断を付け、本文転送後の失敗は標準エラーへ記録します。再現入口は Client の `node tests/tauri-http-diagnostics.cjs` と [説明](../../client/frontend/TAURI.md#http-502-の切り分け) です。
- Node96/96、Rust38/38、オフライン EXE/NSIS 構築、実 EXE の生成 HTTP 故障対照と接続・移行・回退・再試行が通過しました。上流が偽の診断 JSON を返しても任意文字列を記録しないことと、試験プロセスの終了も確認しました。音声の再試験や推論は行っていません。Server の実装は前回77/77と同一です。
- 旧停止の最も整合する説明は、稼働中 HTTP 要求の一時的な転送障害です。ただし当時の情報では拒否接続、接続リセット、timeout、上流502等を区別できず、Windows フィルターやサービス側の一時状態も排除できません。新しい診断は次回の原因特定用であり、根因修正や容錯による根治とは扱いません。接続・音声の再試行方針は変更していません。

## 開始状態とパラメーター表示の修正

- 未選択の入力、出力・監視が両方未選択の場合は開始前に拒否し、理由を開始ボタンの近くに保持します。準備中は実行中と区別し、停止できます。監視音量ゼロは非阻断の説明を表示し、音量やデバイス設定を自動変更しません。
- 倍精度演算の末尾誤差だけを表示から除き、0.35 / 0.30を読みやすくします。実際の非グリッド値、input値、設定送信の精度は保持します。chunkはms、frames、プリセットとカスタムの区別を表示し、0.1秒プリセットの実値約101.333ms / 4,864framesを明示します。extraFrameにも現在の非プリセット値を含め、Legacyの実入力率でframesを表示します。
- 参照配布物の実エントリーを静的に比較しました。既存のgain/indexの刻みと後端単位は変更していません。Clientの変換入力・出力率とServer Deviceの物理率は別フィールドであり、物理44.1kHzだけを開始失敗の原因とは扱いません。
- Node105/105、オフラインEXE/NSIS構築、独立hidden/deny-media EXEの接続・移行・port回退・再試行が通過しました。独立headlessページでは、未選択エラー、準備中停止、失敗後の明示再試行、無効device IDからの復旧、chunk書込・刷新保持、音量表示、ゼロ監視音量の説明を実際に確認しました。このページ検査の媒体・backendは合成です。
- 以上は確認済みのコード欠陥の修正であり、ユーザーの直近試用失敗の唯一の原因を断定するものではありません。真人の有声入力と聴感は別途確認が必要です。502の診断・再試行方針は保持しています。
- 実WebAudioと実VCCを独立headless環境で30秒動作させました。75ブロック / 1,440,000フレームを送受信し、転送エラー・破棄・旧応答はゼロ。入力trackと両出力mediaは活動し、停止後のtrack終了・route停止・試験プロセス終了を確認しました。試験接続橋を使うためRust proxyの実音声検証とは分けます。
- この短測の入力RMS峰は約8.48e-6、出力RMSはゼロでした。通知の転送遅延で発声窓を逃した可能性があり、有声音の変換出力と聴感は確認できていません。Windows出力session採取も停止後となったため、稼働中の物理再生の証明には使いません。追加采音や延長は行わず、次回は確実な開始合図を先に調整します。
